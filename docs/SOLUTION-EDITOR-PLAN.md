# Solution Editor Implementation Plan

## Current Architecture and Scope

The workspace identifies each project by its run ID. `SessionRegistry` calls `runDesign`, which updates `design.md`, the image inventory, and the showcase in the same run directory. A subsequent generation can overwrite those files, so solution cards for older versions need independent snapshots. The project list remains organized by run, with solution versions managed within each project.

Builder calls `plan_showcase` to plan the exhibition. It writes the structured plan to `showcase.md` and uses that same plan to generate `final/00-index.html`. The artifact manifest already points to `showcase.md` through `showcase.direction`. Each version must record the design document (`design.md`), exhibition direction (`showcase.md`), previewable showcase HTML, and required images.

`Canvas.tsx` already supports drag and drop, panning, zooming, connections, undo, and task recovery. The canvas sidebar in `App.tsx` uses `WorkspaceFileList`. The server saves layout through `canvas-store.ts`, while tasks in `editor.ts` accept image file IDs and return a single image. The Solution Editor can reuse these interactions and task states. Solution tasks need their own input, output, and commit contracts.

The first release supports revising, merging, splitting, branching, and deriving further versions within a project. It also supports rearranging a showcase and making targeted changes through prompts. Version comparison and cross-project merging are deferred. Users choose the number of split outputs in the interface. The default is two, and the first release supports two to four.

## 1. Version Storage and Historical Projects

- Add a dedicated solution store under each project run. The version manifest records the version ID, project ID, title, timestamp, source version IDs, task ID, file inventory, cover image, and delivery digest. Store independent file copies initially. Content-based deduplication can follow later.
- Save each new version with its own `design.md`, `showcase.md`, previewable showcase HTML, and required images. Record the relative path and content digest of each document and the page. Also record the cover image ID, exhibition order, and mapping from design image IDs to files. Include `showcase.md` in the delivery digest so changes to the exhibition direction alone produce a distinct version. The server verifies project ownership, manifest membership, and physical paths for all file access, including checks for symlinks that escape the version directory.
- Snapshot completed original deliveries. For an existing project, identify and import the initial version from a valid delivery when versions are first requested. Before starting another generation in the same run, ensure the previous delivery has been snapshotted. Coordinate snapshot reads with writes to the source run so a snapshot cannot mix files from two deliveries. Deduplicate by delivery digest. Show an explanatory empty state when only image-edit outputs exist or the delivery is missing. Import is limited to deliveries still present on disk.
- When importing a historical delivery, preserve `showcase.md` if it can be verified as part of that delivery. If the document is missing or its origin cannot be verified, rebuild it with the existing validation and Markdown serialization when the matching manifest or Builder recovery record contains the full exhibition plan. Record the source of the recovered document. If only partial details remain, such as the cover image or image order, mark the exhibition document as missing and retain the verifiable design document, page, and images. Users can still preview and derive new versions from that snapshot. Derived versions must include a complete `showcase.md`.
- Reuse the static showcase access and security policies, with resource access granted by the version manifest. Provide separate links to each version's showcase, design document, and exhibition direction. Use the existing project export as a compatibility baseline and verify that deliveries containing an exhibition document retain it in the export.

## 2. Task Contracts and Generation

- Add project-level APIs for versions and solution tasks. The client submits a task ID, prompt, operation, expected output count, ordered input versions, and prompt node ID. It can also specify a primary version and the role of each source. The server checks that all inputs exist and belong to the current project. It rejects empty prompts, duplicate inputs, and input or output counts that do not fit the operation.
- Capture the input snapshot on submission. Repeated submissions with the same task ID return the existing record when the payload matches and report a conflict when it differs. A retry reuses the same snapshot and output IDs. Running an edited prompt creates a new task. Track waiting, running, succeeded, failed, cancelled, and interrupted states. On restart, restore persisted state and use commit records to identify completed tasks.
- Extract showcase generation and delivery logic from `design-pipeline.ts` so it can run in a designated output directory. Reuse the Pi SDK, image provider, concurrency slots, and existing validation. Solution tasks read each input version's `design.md`, available `showcase.md`, and image inventory. Editor leads revisions to existing solutions and submits the complete design document and image action plan through `submit_solution_revision`. After the server validates the plan, Builder plans each result independently and produces `showcase.md` and the showcase HTML from the same structured exhibition plan. A layout-only change reuses the design document and original images while saving a new exhibition document and page. Workbench conversations continue to use `runDesign`. Solution tasks run through a separate entry point to protect the source run.
- For each output, Editor specifies whether to reuse an image from a particular version, edit an existing image, or generate a new one. Editor copies stable source image references from the input inventory. The server validates each reference and reports the affected output image and available references to Editor, with a limited number of correction attempts. It writes images to the output directory after validation. Layout-only changes reuse all design images, and targeted edits reuse the remaining images according to the plan. When merging, qualify image IDs with the source version ID to avoid naming collisions and reconcile the corresponding references in the documents.
- Build all outputs from a split in the task staging area. Before committing, validate the planned images in `design.md`, the cover image and exhibition entries in `showcase.md`, the image inventory, and HTML references for each result. The cover image must belong to the version. Each planned image must appear once in the exhibition direction and be visible on the page. Page resources must come from that version's manifest. Publish the batch in a single commit once every result passes validation. A cancellation or failure before the commit leaves the version list unchanged. After the commit, recovery uses the commit record. Stable output IDs and atomic commits prevent duplicates during concurrent submissions or restarts.

## 3. Workspace Interaction and Compatibility

- Rename the Canvas entry to **Solution Editor** and show the current project's versions in the left panel. Version cards show a cover, title, image count, and source summary. Users can drag a version onto the canvas, add it with a button, or open its showcase, design document, and exhibition direction. Indicate when a historical version lacks an exhibition document. Reuse the existing sidebar behavior on mobile.
- Provide a single prompt card type. Incoming image connections trigger image editing, and incoming solution connections trigger solution editing. Infer the solution operation from the prompt and inputs, with controls to override the operation and supply required parameters. In the initial interaction design, users can connect mixed inputs and are prompted to disconnect one input type before running the card. Inputs connect on the left, and outputs appear on the right. Validate connection types, duplicates, and cycles when saving. Start tasks only on explicit execution and reuse the existing progress, retry, and cancellation interactions.
- Extend saved canvas data with solution cards, version IDs, and solution task references. Preserve existing images, prompts, connections, viewport, and layout through backward-compatible reads. Normalize legacy image and solution prompt cards to the shared prompt type while retaining their nodes and connections. New executions use current incoming connections. Retries of older tasks use their original submission records. Derive result card IDs from task and output IDs so reapplying a result after refresh is idempotent. Removing cards or undoing layout changes preserves committed versions and their source records.

## 4. Implementation Sequence and Acceptance Criteria

1. Implement version storage, initial version import, version file access, and access tests. Cover three historical cases for the exhibition document: import as-is, verified reconstruction, and missing. Verify that older versions can still open their files after the source run updates its exhibition document and page.
2. Deliver the single-input, single-output flow with the revision stage and showcase delivery. Use a controlled provider to test generation, layout-only changes, targeted replacement, and retries. Verify that layout-only changes preserve the design document and image contents and that the new exhibition document and page reflect the updated arrangement. Reject new results with a missing exhibition document or inconsistent references before committing.
3. Add multi-input merging and multi-output splitting. Test input order, duplicate image names from different sources, independent exhibition documents, atomic batch commits, concurrent duplicate submissions, cancellation, and restart recovery.
4. Integrate the workspace sidebar and canvas. In browser tests, cover drag and drop, adding versions with a button, deriving from historical versions, merging, splitting, reconnecting outputs, refresh recovery, and error feedback. Include legacy canvases, image editing, project preview, and export.
5. Run `npm run check`, `npm run build`, relevant server tests, and browser regressions. Record what was verified with simulated and live providers. Check that no generated workspace files are included in the commit.

## Acceptance Record

- Solution tasks run serially within a project. Later submissions wait and can be cancelled before they start. Server process tests cover retrying after a forced exit before commit and recognizing success from existing versions after a restart following commit.
- Simulated providers cover revision, rearrangement, targeted replacement, merging, and splitting. Tests include asset reuse, concurrent deduplication, cancellation, and withholding an entire batch when a result fails. Browser regressions cover waiting, cancellation, failure feedback, retry, and canvas recovery after refresh.
- A browser test used the configured live reasoning provider in a temporary workspace to rearrange the showcase of a synthetic solution. It verified that the new showcase opened with the original images and that both Markdown documents could be opened separately. Image generation and image editing were verified with simulated providers.
- ZIP export tests compare the archived `showcase.md` byte for byte against the source. Test artifacts are written to a temporary directory.
